# CLAUDE.md — create-express-modular CLI

This document outlines project commands, architectural principles, and coding standards for developers contributing to the `create-express-modular` repository.

## Commands

### Build & Package Commands
- **Build the CLI**: `npm run build` (uses `tsup` to compile `./src` to `./dist`)
- **Execute Local Build**: `node dist/bin/cli.js [args]` or link/run via your package manager.
- **Prepublish Check**: `npm run prepublishOnly` (automatically runs build first)

## Coding Guidelines & Style

### 1. File Structure & Splitting
- **Separate View/Template from I/O**: String-scaffolders must be pure functional templates (`templates.ts`). Orchestration, inquirer prompts, and I/O writes go in `index.ts`.
- **Maintain Public Entry Points**: Keep flat files like `authGenerator.ts` and `moduleGenerator.ts` as thin re-export shims if their underlying implementations move to subdirectories. This preserves `tsup.config.ts` bundle entry points.
- **Extract Shared Utils**: Common logic (e.g., `pluralize()`, `capitalize()`, `injectRoute()`, `copyFolderSync()`) must not be duplicated. Always import from `src/lib/utils/`.

### 2. TypeScript & Imports
- **Strict Typing**: Ensure all function parameters and return values have explicit types.
- **Type-Only Imports**: Import configuration structures and inquirer types using `import type`.
- **Absolute vs Relative**: Use relative imports inside `src/`.

### 3. Syntax & Style Standards
- **No `'use strict'`**: The build pipeline compiles to strict ESM/CJS standards automatically. Do not manually write `'use strict'` at the top of TS files.
- **Enforced JSDoc**: Every exported function, class, and interface must have a comprehensive JSDoc block detailing its purpose, parameters (`@param`), and return type/value (`@returns`).
- **Ansi/Log Outputs**: Never use bare `console.log` for warnings, errors, or success messages. Delegate formatting to functions in `src/lib/ui.ts` to ensure consistent CLI styling.
- **Comment Conventions**: Avoid blocky divider comments (e.g., `// ─── HELPER ────────`). Use simple line breaks and inline comments where explanatory text is actually needed.
